# v2.0 Container Migration — Pitfalls Discovered 2026-06-16

## Migration Summary
Transformed La Gazzetta di Kyiv from 20-page INTEL/ALPHA architecture to 9-page 6-container dashboard:
- **6 domain containers**: Monetary Order (52), Energy & Resources (68), Technology & AI (172), Information & Narrative (0), Biosecurity & Health (0), Flashpoints (85)
- **377 stories soft-archived** with `container` + `thesis` columns, `story_tags` table
- **5 Cloud Scheduler jobs paused permanently**, 1 pipeline cron paused during deploy
- **Architecture**: Agent = sole DB writer, Cloud Run pipeline reads DB from GCS

## Pitfall 1: Hashed Asset Self-Nuke (deploy_routine.sh Cleanup Order)

### The Bug
`deploy_routine.sh` ran `build_hashed_assets.py` (generates `app.fa4839a6.js`), then ran cleanup `find -delete` lines that matched and deleted ALL hashed JS/CSS files — including the ones just generated. GCS rsync uploaded HTML referencing `app.fa4839a6.js` but the file itself was deleted before upload.

### Detection
```bash
curl -s "https://www.lagazzettadikyiv.com/" | grep 'app\.'
# Shows: <script src="./app.fa4839a6.js"></script>
gsutil ls "gs://www.lagazzettadikyiv.com/app.fa4839a6.js"
# Returns: NOT FOUND or CommandException
```

### Root Cause
Pipeline stage order was:
```
Stage 2.1: build_hashed_assets.py  → creates app.fa4839a6.js
Stage 2.5: test_platform.py
Cleanup: find ... -delete           → DELETES app.fa4839a6.js
Stage 4: GCS rsync                 → uploads HTML but NOT the hashed file
```

### Fix
Move cleanup BEFORE build_hashed_assets so only OLD hashes are purged:
```bash
# BEFORE Stage 2.1:
find "$PROJECT/public" -maxdepth 1 -name 'app.*.js' ! -name 'app.js' -delete

# Stage 2.1:
$PYTHON "$PROJECT/scripts/build_hashed_assets.py"

# Stage 2.5:
$PYTHON "$PROJECT/scripts/test_platform.py"
# NO cleanup after — hashed files survive for GCS upload
```

## Pitfall 2: Duplicate Script Tags (Footer Template + build_site.py)

### The Bug
`templates/footer.html` contained `<script src="./app.js">` AND `build_site.py` injected `<script src="./app.js">` in the body after `<!-- COMPONENT:FOOTER:END -->`. Result: `app.fa4839a6.js` loaded twice. The browser executed the IIFE twice — the second execution found `window.Gazzetta` already defined and aborted silently, leaving 0 containers rendered.

### Detection
```bash
curl -s "https://www.lagazzettadikyiv.com/" | grep 'script.*src'
# Shows duplicate: app.fa4839a6.js appearing twice
```
```js
// Console: Gazzetta loaded: undefined | containers: 0
// No JS errors — silent failure
```

### Fix
Remove `app.js` from `templates/footer.html`. Only `i18n.js` belongs in the footer (data-i18n attributes need it before DOM loads). `build_site.py` injects `app.js` once in the body, after all containers are defined.
```html
<!-- templates/footer.html — CORRECT -->
<script src="./i18n.js"></script>
<!-- app.js loaded by build_site.py -->
```

## Pitfall 3: DB Schema Migration Invisible to Cloud Run

### The Bug
Running `ALTER TABLE stories ADD COLUMN container TEXT` locally migrates the local `gazzetta.db`. But the Cloud Run pipeline downloads `gazzetta.db` from GCS at startup — and GCS has the PRE-migration copy. `db_to_json.py` v2.0 references `story_tags` table → `sqlite3.OperationalError: no such table: story_tags` → pipeline exits 1 before any deploy.

### Detection
```bash
gcloud logging read "resource.type=cloud_run_job AND resource.labels.job_name=gazzetta-pipeline" --limit=10
# Shows: "ABORT: db_to_json.py FAILED" / "no such table: story_tags"
```

### Fix
After ANY schema migration (CREATE/ALTER/DROP), upload the migrated DB to GCS immediately:
```bash
gsutil cp gazzetta.db gs://www.lagazzettadikyiv.com/gazzetta.db
```
Then execute the pipeline — it will download the migrated DB and work correctly.

### Prevention Rule
**Schema migration protocol**: migrate locally → test db_to_json.py → upload DB to GCS → execute pipeline. Never wait for the next pipeline cycle — it will fail.

## Pitfall 4: Cloud Run `:latest` Tag Resolution Lag

### The Bug
After `gcloud builds submit --tag ...:latest`, the Cloud Run job was immediately executed with `--wait`. Despite the new image being pushed, Cloud Run used the cached `:latest` from before the push — the fix wasn't applied. The pipeline ran with the buggy `deploy_routine.sh` and produced the same failure.

### Detection
Check if the pipeline log shows expected behavior (e.g., no cleanup after Stage 2.1):
```bash
gcloud logging read "resource.type=cloud_run_job AND..." --limit=50 | grep "Stage 2.1"
```

### Fix
Always pin the exact sha256 digest for critical image updates:
```bash
# 1. Build and capture digest from output
gcloud builds submit --tag IMAGE:latest 2>&1 | grep "digest: sha256:"

# 2. Update job with pinned digest
gcloud run jobs update gazzetta-pipeline --region=europe-west1 \
  --image=europe-west1-docker.pkg.dev/PROJECT/gazzetta-docker/gazzetta-pipeline@sha256:XXXX

# 3. Execute
gcloud run jobs execute gazzetta-pipeline --region=europe-west1 --wait
```

### When Usage Is Forgiving
For non-critical updates or when the next scheduler cycle will pick up `:latest` within minutes, `:latest` is fine. For "must deploy NOW" after fixing a blocking bug, always pin the digest.

## v2.0 Architecture Changes (Quick Reference)

| Aspect | v1.x (before) | v2.0 (after) |
|--------|--------------|--------------|
| Containers | INTEL/ALPHA dropdowns | 6 collapsible domain containers |
| HTML pages | 20 | 9 |
| Stories | All in one list | Classified into 6 containers |
| DB schema | `stories` table only | + `container`, `thesis` columns + `story_tags` table |
| Pipeline scripts | 43 Python files | ~5 core scripts |
| DB writer | 3 concurrent (Agent, Cloud Run, cron) | Agent only (single-writer) |
| Cloud Scheduler jobs | 7 active | 2 active (pipeline + cdo-auditor) |
| App.js loading | In footer template + body (double) | In body only (single) |
| Hashed asset generation | After cleanup (self-nuked) | Before cleanup (preserved) |
| i18n.js | Footer template | Footer template (correct — data-i18n attributes need it early) |
