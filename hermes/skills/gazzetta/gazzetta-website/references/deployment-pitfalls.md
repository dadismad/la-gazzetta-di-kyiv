# GitHub Pages Deployment — Common Failures & Fixes

## Symptom: Site returns 404 after push

### Cause 1: Quality gate scripts are outdated
The deploy workflow (`refresh-and-deploy.yml`) runs three scripts before uploading artifacts:
- `ops/ui_contract_check.py`
- `ops/brandbook_enforcer.py`
- `ops/claims_container_guard.py`

When the design system changes (palette, fonts, layout, container structure), these scripts detect violations and produce `"ok": false`. While they don't block the workflow directly (they exit 0), the CEO hard gate in the workflow reads `data/deploy_canary_report.json` and `data/ceo_status.json` — if those are stale, deployment may fail or produce a broken site.

### Fix
1. Update all three gate scripts to match the current design system
2. Update `data/deploy_canary_report.json` — set `"passed": true` with current checks
3. Update `data/ceo_status.json` — set `"state": "running"` with empty `blocked_reasons`
4. Run all three locally: `python3 ops/ui_contract_check.py && python3 ops/brandbook_enforcer.py && python3 ops/claims_container_guard.py` — all must output `"ok": true`
5. Push

### Cause 2: GitHub Pages not enabled or wrong source
The workflow uses `actions/deploy-pages@v4` which requires Pages to be enabled in repo settings. If Pages is disabled, the deploy step silently fails.

### Fix
Go to `github.com/<user>/<repo>/settings/pages`:
- Set Source: "Deploy from a branch" → `main` or `gh-pages` → `/ (root)` 
- Or verify "GitHub Actions" source is enabled if using the workflow
- Wait 60s for CDN propagation

### Cause 3: Cache serving stale 404
GitHub Pages CDN caches 404s as aggressively as 200s. If a previous deployment failed, the CDN may serve the cached 404 for up to 10 minutes (HTTP `age` header shows cache duration).

### Fix
- Wait. The cache expires automatically.
- Use `curl -sI` to check the `age` header — when it resets, new content is live
- Bump cache-bust versions on CSS/JS (`?v=N`) to force fresh loads

### Cause 4: Stale deploy status files falsely claiming "all OK"
The `data/ceo_status.json` and `data/deploy_canary_report.json` files are generated by local scripts and can claim `"ok": true` / `"passed": true` even when the live site is not deployed. This happens when:
- The files are regenerated from a local build that succeeded, but the push or Pages deploy failed
- The files are checked into git with old data from a prior successful deploy
- A new cycle ran locally but the `git push` never happened or GH Actions workflow silently failed

The `external_checks` in `ceo_status.json` can carry `status: 200` and `size: 10800` from a check that ran against stale local data or a previous deploy — they do NOT reflect the current live site state.

### Fix
Never trust the status files alone. Always verify the live site independently:
```bash
curl -sI "https://pureciclismo.github.io/gazzetta-di-kyiv/" | grep -q "200" && echo "LIVE" || echo "SITE DOWN"
```
The `gazzetta-editorial-writer` skill's Step 9 quality gate now includes this as a blocking check. Also verify that `pureciclismo.github.io` itself returns 200 (not 404) — the org-level site returning 404 means the org may not have Pages enabled at all.

## Prevention Checklist (after every design change)
```
[ ] Run all three gate scripts locally → all ok: true
[ ] Update deploy_canary_report.json → passed: true
[ ] Update ceo_status.json → state: "running", blocked_reasons: []
[ ] Bump CSS/JS cache-bust versions in index.html
[ ] Commit and push
[ ] Wait 120s for CDN
[ ] Verify with curl -sI → HTTP/2 200
[ ] Do NOT trust status files alone — curl the live URL independently
```

## Google Cloud Storage Deployment (alternative to GitHub Pages)

When GitHub Pages is unavailable (private repo, billing issues) or when deploying to a custom domain on GCP.

### Prerequisites
- `gcloud` CLI installed and authenticated: `gcloud auth login`
- Google Cloud DNS zone managing the domain (nameservers pointing to `ns-cloud-b*.googledomains.com`)
- Project selected: `gcloud config set project <PROJECT_ID>`

### Step-by-step deployment

```bash
# 1. Create storage bucket (use generic name if domain not yet verified)
gsutil mb gs://<bucket-name>

# 2. Configure static website hosting
gsutil web set -m index.html -e index.html gs://<bucket-name>

# 3. Make bucket publicly readable
gsutil iam ch allUsers:objectViewer gs://<bucket-name>

# 4. Upload site files
gsutil -m cp -r site/* gs://<bucket-name>/

# 5. Verify: curl -sI https://storage.googleapis.com/<bucket-name>/index.html → 200
```

### Custom domain mapping (requires domain verification)

```bash
# Verify domain ownership FIRST at https://search.google.com/search-console
# Then create domain-named bucket:
gsutil mb gs://lagazzettadikyiv.com

# Add CNAME record to Google Cloud DNS zone
gcloud dns record-sets transaction start --zone=<zone-name>
gcloud dns record-sets transaction add \
  --zone=<zone-name> \
  --name="www.lagazzettadikyiv.com." \
  --type=CNAME --ttl=300 \
  "c.storage.googleapis.com."
gcloud dns record-sets transaction execute --zone=<zone-name>
```

### Pitfall: Domain verification required for domain-named buckets

Google blocks `gsutil mb gs://example.com` with `AccessDeniedException: 403` unless the domain is verified in Google Search Console. Workarounds:
- **Verify domain** via Search Console (DNS TXT record method — add record to Google Cloud DNS zone)
- **Use generic bucket name** (e.g., `gazzetta-site`) with load balancer, or use the direct `storage.googleapis.com` URL temporarily
- **Use Cloudflare Pages** as alternative (simpler, no verification needed, deploys from git)

### Pitfall: Service account key creation blocked by org policy

Google's "Secure by Default" enforces `iam.disableServiceAccountKeyCreation`. Workaround: use `gcloud auth login` with human account — browser-based OAuth flow bypasses the key restriction. The authenticated session persists for gcloud/gsutil commands.

### Pitfall: `gsutil rsync` silently skips files with size mismatches (June 2026)

`gsutil -m rsync` uses mtime + size comparison by default, not checksums. When two files have different sizes but rsync's metadata check doesn't detect the difference (e.g., the source file was modified by a pipe/sed operation that changed size from 13,890 to 13,868 bytes, but rsync's internal comparison logic only registers the mtime as newer on DST and skips), the file is NOT synced. The destination keeps the old version.

**Symptom:** `gsutil rsync -r gs://source-bucket/ gs://dest-bucket/` reports "Copying mtime from src to dst" for story.html (only updating the timestamp), but does NOT copy the file content. The destination file has a newer timestamp but OLD content.

**Root cause:** When the source bucket's file has an older mtime than the destination, rsync may skip the copy even when sizes differ. This happens when the source was overwritten with a different version that has a different size but the mtime comparison wins.

**Fix — force-upload with gsutil cp:** After any rsync that involves HTML files, verify critical files were actually copied:
```bash
gsutil ls -l gs://dest-bucket/story.html  # Check size and mtime
gsutil cat gs://dest-bucket/story.html | grep 'expected-string'  # Verify content
```
If the content doesn't match the source, force-copy:
```bash
gsutil cp gs://source-bucket/story.html gs://dest-bucket/story.html
```

**Prevention:** After any bucket-to-bucket sync, spot-check 3-5 critical HTML files with `gsutil cat | grep` to verify content landed. Don't trust rsync output alone — it can report "Copying" while only updating metadata.

### Pitfall: Dual-bucket disconnect — LB serves from one bucket, pipeline deploys to another (June 2026)

The GCP Load Balancer's backend bucket may point to `www.lagazzettadikyiv.com` while the pipeline's `cloud_entrypoint.py` uploads to `lagazzettadikyiv.com` (without www). Both buckets exist, both have similar files, but they diverge silently. The live site serves STALE content while the pipeline reports "deploy successful."

**Symptom:** `curl https://lagazzettadikyiv.com/story.html` shows hashed script references (`app.a744a56e.js`), but `curl https://www.lagazzettadikyiv.com/story.html` shows unhashed cache-busters (`app.js?t=...`). The browser loads stale content. `gsutil ls` on both buckets shows different file sizes for the same HTML files.

**Detection:**
```bash
# 1. Check which bucket the LB points to
gcloud compute backend-buckets describe gazzetta-backend | grep gcsBucketName

# 2. Check which bucket the pipeline deploys to
grep 'BUCKET_NAME' cloud_entrypoint.py

# 3. Verify they match
gsutil ls -l gs://<lb-bucket>/index.html
gsutil ls -l gs://<pipeline-bucket>/index.html
# If different sizes/timestamps → disconnect confirmed
```

**Fix:** Either (A) update the backend bucket to match the pipeline's target, or (B) update `cloud_entrypoint.py` to match the LB's bucket. Option A is simpler (one gcloud command). Option B is safer long-term (many scripts reference the www bucket — see `grep -rn 'lagazzettadikyiv\.com' scripts/`).

**Prevention:** After any GCP infrastructure change, verify the full chain: pipeline bucket → LB backend → live URL. Run `curl -s https://<domain>/story.html | grep 'script src'` on EVERY deploy to confirm the correct JS files are referenced.

When `build_hashed_assets.py` rewrites HTML files to reference hashed JS/CSS (e.g., `app.a744a56e.js` instead of `app.js`), the `gsutil rsync -d -r` command may NOT upload the new HTML files because the CDN or GCS already has files with the same name from a previous deploy. The browser continues loading the old unhashed URLs (`app.js?v=sprint4`) which reference the OLD JS — none of the new functions exist.

**Symptom:** Browser console shows correct hashed JS URL, but `typeof populateHeroIndicators === 'undefined'` when the function clearly exists in the hashed file. The browser is loading the OLD `app.js` (unhashed) because the HTML still references `app.js?v=sprint4` instead of `app.a744a56e.js`.

**Root cause:** `gsutil rsync` with `-d` (delete extraneous) may skip files that appear unchanged at the GCS metadata level. The rewritten HTML has the same filename and similar size, so rsync doesn't detect a change.

**Fix — force-upload all HTML with cache bust:**
```bash
cd ~/lagazzettadikyiv
for f in public/*.html; do
  gsutil -h "Cache-Control:no-store,max-age=0" cp "$f" "gs://www.lagazzettadikyiv.com/$(basename $f)"
  gsutil -h "Cache-Control:no-store,max-age=0" cp "$f" "gs://lagazzettadikyiv.com/$(basename $f)"
done
```

**Prevention:** After `build_hashed_assets.py`, always force-upload HTML files individually with `Cache-Control:no-store`. Do not rely on `rsync` for HTML after hashing changes.

**Verification:** Check a deployed HTML file for hashed references:
```bash
gsutil cat gs://www.lagazzettadikyiv.com/index.html | grep -oE 'app\.[a-f0-9]+\.js'
# Must output: app.a744a56e.js (NOT app.js)
```

And in the browser console:
```js
document.querySelector('script[src*="app."]').src
// Must show hashed URL, NOT "app.js?v=sprint4"
```

When deploying CSS changes, bumping the version string (`?v=25.16`) does NOT guarantee fresh delivery if the CDN edge already saw that URL with the old content. The edge cache can serve the old CSS for hours even with `Cache-Control: must-revalidate` on the origin.

**Symptom:** Browser loads `styles.css?v=25.16`, `curl` confirms the new CSS is on GCS, but `getComputedStyle()` still shows old values (0px borders, no shadows).

**Root cause:** Between the CSS deploy and the HTML deploy (or during a failed deploy), the CDN edge cached the old CSS at the bumped URL. Subsequent requests for `?v=25.16` hit the stale edge cache.

**Fix pattern — double bump + timestamp cache-breaker:**
```bash
# 1. Deploy CSS FIRST
gsutil cp site/styles.css gs://www.lagazzettadikyiv.com/styles.css
# 2. Bump version string in all HTML files to a FRESH value
sed -i '' 's/?v=25.16/?v=25.17/g' *.html
# 3. Deploy HTML SECOND
gsutil -m cp site/*.html gs://www.lagazzettadikyiv.com/
# 4. Verify with a timestamp cache-breaker to bypass CDN edge
browser_navigate("https://www.lagazzettadikyiv.com/page.html?cb=1768136400")
```

**Prevention:** Always use a fresh timestamp-based cache breaker for browser verification after deploy. Never trust that `?v=N` alone busted the CDN edge.

### Pitfall: JS helper function references out-of-scope variable from parent IIFE (June 2026)

When a helper function defined inside an IIFE uses a variable (`t` for i18n) that is only defined in a sibling function's local scope, the helper throws `ReferenceError: t is not defined` at runtime. The error is silent in the browser (caught by the async init's error path), and the page shows "Loading intelligence report…" permanently.

**Symptom:** Story detail page (`story.html?id=481`) shows "Loading intelligence report…" forever. `browser_console` reveals: `ReferenceError: t is not defined at renderMultiPersona`. The `t` function (i18n shorthand) is defined inside `buildHTML()` as `const t = window.i18n ? (k, fb) => i18n.t(k, fb) : (k, fb) => fb;` but `renderMultiPersona(story)` is a separate function that tries to call `t('multi_persona_label', ...)`.

**Root cause:** The IIFE structure:
```js
(function() {
  function buildHTML(story) {
    const t = (k, fb) => i18n.t(k, fb);   // t scoped HERE only
    return `...${renderMultiPersona(story)}...`;  // calls without passing t
  }
  function renderMultiPersona(story) {
    return '<h2>' + t('multi_persona_label') + '</h2>';  // t undefined HERE
  }
})();
```

**Fix:** Pass `t` as a parameter:
```js
// Line 134: change call
${renderMultiPersona(story, t)}

// Line 145: change signature
function renderMultiPersona(story, t) {
```

**Detection:** `grep -n 'renderMultiPersona' public/story-app.js` — the call site must pass `t`, the function signature must accept `t`. If the call shows `${renderMultiPersona(story)}` without the second argument, the bug is present.

**Prevention:** Any helper function that uses `t` (i18n) must either (A) accept it as a parameter from `buildHTML()`, or (B) define its own `const t = ...` fallback. Option A is cleaner and avoids duplicate fallback logic.

When CSS changes span multiple `execute_code` blocks, the `site/styles.css` can fall behind `styles.css` if only the first block includes the `cp` command.

**Symptom:** Local `styles.css` = 67KB (has new rules). `site/styles.css` = 62KB (stale). `gsutil cp site/styles.css` deploys the stale version. `curl` confirms new rules are missing from live CSS.

**Root cause:** Block 1: `echo '...' >> styles.css && cp styles.css site/ && gsutil cp ...`. Block 2: `echo '...' >> styles.css` but NO `cp styles.css site/`. Block 2 deploys HTML but uses stale `site/styles.css`.

**Fix:** After ANY CSS modification, always verify `site/styles.css` matches:
```bash
echo "Local: $(wc -c < styles.css) bytes  Site: $(wc -c < site/styles.css) bytes"
```
If sizes differ, re-copy: `cp styles.css site/styles.css`. Re-deploy CSS separately after HTML deploy to GCS.

### Pitfall: DNS TXT record conflict with existing SPF records

When adding a Google Search Console verification TXT record to a Google Cloud DNS zone that already has an SPF TXT record, `gcloud dns record-sets create` returns `HTTPError 409: already exists`. This is because DNS treats all TXT records for the same name as a single RRset — you cannot `create` a second one.

**Fix:** Use a transaction to atomically replace the TXT recordset with both values:
```bash
gcloud dns record-sets transaction start --zone=<zone>
gcloud dns record-sets transaction remove --zone=<zone> --name="domain.com." --type=TXT --ttl=300 '"v=spf1 ..."'
gcloud dns record-sets transaction add --zone=<zone> --name="domain.com." --type=TXT --ttl=300 '"v=spf1 ..." "google-site-verification=..."'
gcloud dns record-sets transaction execute --zone=<zone>
```

This replaces the single-value TXT record with a multi-value one. Both the SPF and verification strings are preserved. Verify with `dig +short TXT domain.com`.

When nameservers point to `ns-cloud-b*.googledomains.com`, the DNS zone is managed in Google Cloud DNS, NOT at the registrar (Spaceship, GoDaddy, etc.). DNS records must be added via `gcloud dns record-sets`, not the registrar's DNS interface. The registrar's "DNS records missing" warning is expected — it sees Google's nameservers and can't read the records within them.

## Masthead Symbol Consistency (v26.2 — June 2026)

### Symptom: Caduceus appears on homepage but not sub-pages

The caduceus SVG (`.masthead-caduceus`) is only present in `site/index.html`'s `.masthead-left`. All sub-pages (`stories.html`, `flows.html`, `trades.html`, `signal.html`, `track.html`, `flow-nodes.html`, `event_horizon.html`) only have `.masthead-bulava` in `.masthead-left` — the caduceus is completely absent.

### Fix
```bash
# Verify caduceus presence across ALL pages
for page in stories flows trades signal track flow-nodes event_horizon; do
  grep -c 'masthead-caduceus' "site/${page}.html"
done
# Each should output 1. If any output 0, fix by adding caduceus.
```

Add `<span class="masthead-caduceus">[caduceus SVG]</span>` inside `.masthead-left` on every sub-page, BEFORE the bulava span and the name link. Extract the exact SVG from `site/index.html`.

### Symptom: Bulavas on wrong side (LEFT instead of RIGHT)

Per design v26.1 spec: caduceus LEFT, bulavas RIGHT. On sub-pages, bulavas are inside `.masthead-left` instead of `.masthead-right`. Move them to `.masthead-right` next to the product-nav or nav buttons.

## Gold Border Consistency (v26.2)

### Symptom: Front page cards have gray borders, stories page has gold

Cards on index.html (`.hero-ind`, `.side-section`, `.svc-card`) use `border: 1px solid var(--divider)` (gray #E5E7EB). Stories page cards have `border-left: 2px solid #D4AF37` (gold). Spec says ALL cards must have gold 2px left border.

### Fix in styles.css
```css
.hero-ind, .side-section, .svc-card {
  border: none;
  border-left: 2px solid var(--gold);  /* #D4AF37 */
}
```

### Verification
After deploy, use browser_vision on front page — ALL cards (hero indicators, side sections, service cards) must show visible gold left border.
